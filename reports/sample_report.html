NHIs found

This assessment identified 19 non-human identities in the Okta tenant and 2 findings requiring action within 24 hours. The most significant is terraform-okta-provider: API token is owned by a user account that is no longer active (DEPROVISIONED).

The pattern across these findings is ownership rather than configuration. Individually, most of the issues below are the result of a reasonable decision made quickly — a token issued to unblock a deployment, an admin role granted to fix a failing sync, a scope set to manage because it was simpler than working out which read scopes were needed. What makes them risk rather than debt is that no person or team currently owns any of these identities, so nothing causes them to be revisited. Okta provides no owner field for tokens, hooks or service integrations, which means ownership has to be maintained deliberately or not at all.

The inventory in section 2 lists all 19 identities. For most organisations this list has never previously been assembled, and it is worth reviewing on its own terms — before considering the findings — simply to establish whether every entry is recognised.

critical NHI-001 Org API token

API token is owned by a user account that is no longer active (DEPROVISIONED).

terraform-okta-provider  ·  00Torphaned000000EXAMPLE
Evidence

Token 'terraform-okta-provider' (id 00Torphaned000000EXAMPLE) was created on 2025-05-28 by wes.brennan@example.com, whose Okta account is currently DEPROVISIONED. The token was last used 430 days ago.

Business risk

An Okta API token carries the administrative privileges its creator held at the moment it was issued, and those privileges do not change when the creator's account is deactivated. This credential still has whatever access wes.brennan@example.com had, but there is no longer a person accountable for it, no one who knows what uses it, and no one who would notice if it were stolen. Offboarding removed the human and left the credential behind. Because the 30-day expiry clock resets on every use, an automated job keeps this token alive indefinitely.

Remediation

Revoke immediately: Admin console -> Security -> API -> Tokens -> revoke this token. Before revoking, identify what uses it by filtering the System Log on this token and coordinating a replacement. Reissue as an API Service Integration with only the scopes the workload actually needs, owned by a team rather than a person. Add 'revoke API tokens created by this user' to the offboarding checklist.

critical NHI-002 Service account (user object)

Suspected service account holds the Super Administrator administrative role.

svc-jira@example.com  ·  00uSVCJIRA0000EXAMPLE
Evidence

svc-jira@example.com was assessed as a non-human identity (heuristic score 1.00: login matches service-account naming convention (svc-, integration); no MFA factor enrolled; no interactive browser sign-in in the System Log window; 480 API events attributed to this actor) and holds Super Administrator, assigned 2024-11-29. MFA enrolled: no.

Business risk

svc-jira@example.com holds Super Administrator, which grants complete administrative control of the tenant, including the ability to create further admins, disable MFA policies, modify authentication rules, and access every application. This account shows the behaviour of software rather than a person: it does not sign in interactively, and its credential is therefore stored somewhere — a CI secret, a configuration file, a script, a password manager entry shared across a team. Because no MFA factor is enrolled, that stored credential is the only thing standing between an attacker and this level of access. There is no second factor to fail closed. In practical terms, anyone who obtains this credential owns the identity provider — and therefore owns every application behind it. They can create themselves a persistent admin account, weaken MFA policy, and read or grant access to any connected SaaS system. Identity provider compromise is the standard opening move in recent SaaS breaches precisely because it collapses every other control at once. There is also no accountable owner: if this credential were used maliciously tomorrow, the audit trail would name a service account, and nobody could say who was responsible for it.

Remediation

Treat as urgent. 1) Determine what svc-jira@example.com actually does by filtering the System Log on this actor over the last 90 days. 2) Identify the minimum role that covers those operations — in nearly all cases a scoped custom admin role, or no admin role at all, is sufficient. 3) Replace the Super Administrator assignment with that scoped role: Admin console -> Security -> Administrators -> select the account -> edit assignments. 4) Migrate the workload to an API Service Integration with explicit scopes, so access is granted to a workload rather than inherited from a user object. 5) Record a named owning team on the account. Do not simply delete the role before step 1 — you will break something and not know what.

high NHI-003 Event / inline hook

Active event hook delivers identity data over plaintext HTTP.

legacy-audit-forwarder  ·  who002EXAMPLE
Evidence

Hook 'legacy-audit-forwarder' (who002EXAMPLE) is ACTIVE and posts to http://audit-collector.thirdparty-vendor.example.net/ingest. The scheme is http, not https. Events sent: user.session.start. Auth scheme configured: none. Verification status: UNVERIFIED.

Business risk

Every time this hook fires, your identity provider sends user data — logins, names, session events — across the network unencrypted. Anyone positioned between Okta and audit-collector.thirdparty-vendor.example.net can read it, and if an auth header were configured they would read that credential too, in the clear, on every request. The destination is a third-party domain, so the traffic leaves your control entirely. This is the kind of finding that appears in a SOC 2 report as an encryption-in-transit exception.

Remediation

Move the endpoint to HTTPS with a valid certificate and update the hook: Admin console -> Workflow -> Event Hooks -> legacy-audit-forwarder. If the destination cannot support TLS, the integration should be retired rather than fixed. Confirm who owns audit-collector.thirdparty-vendor.example.net and whether this integration is still required at all — hooks pointing at long-forgotten vendors are common.

high NHI-004 API service integration (OAuth)

API service integration holds tenant-control scopes that are broader than a read-only workload requires.

Internal Provisioning Service  ·  0oaAPISVCPROV0EXAMPLE
Evidence

'Internal Provisioning Service' (0oaAPISVCPROV0EXAMPLE) is granted: okta.apps.read, okta.groups.manage, okta.users.manage. Of these, okta.groups.manage, okta.users.manage permit write operations against core identity objects. Read-only equivalents exist for each (okta.groups.read, okta.users.read).

Business risk

'Internal Provisioning Service' authenticates with a client ID and secret and no human is involved in the flow, so its access is entirely determined by the scopes granted to it. Those scopes currently include write access to core identity objects: okta.groups.manage allows it to create and modify groups and their membership — and therefore change who has access to what; okta.users.manage allows it to create, modify, deactivate and reset credentials for any user in the org. If the client secret leaks — from a CI log, an environment variable dump, a compromised laptop, or a repository — an attacker obtains that same write access, and it looks like normal integration traffic in the log. The narrower point is governance: nobody can currently state what this integration writes, which means nobody can state what an attacker holding its secret could change. Okta's own guidance is to grant the least-privileged scope that lets the workload function, so this is measured against the vendor's stated standard rather than an external one.

Remediation

Establish what write operations this integration actually performs — filter the System Log on this client_id (0oaAPISVCPROV0EXAMPLE) and look for anything beyond reads. If the traffic is read-only, replace each .manage scope with its .read equivalent: Admin console -> Applications -> Internal Provisioning Service -> Okta API Scopes -> revoke the .manage grant and grant .read. If some writes are genuinely needed, grant only the specific scopes covering them and record why in a comment or ticket, so the next reviewer does not have to rediscover it. Okta's guidance on scoping API service integrations is to grant the narrowest scope that permits the workload to function.

high NHI-005 SCIM provisioning connection

SCIM provisioning remains configured on an application that is INACTIVE.

Zoom (legacy - migrated off 2025)  ·  0oaSCIMZOOM000EXAMPLE
Evidence

'Zoom (legacy - migrated off 2025)' (0oaSCIMZOOM000EXAMPLE) has status INACTIVE but USER_PROVISIONING is still ENABLED with capabilities: create users, update profiles, deactivate users.

Business risk

When Zoom (legacy - migrated off 2025) was switched off in Okta, the API credential Okta holds for the downstream system was almost certainly not revoked on the other side. That credential typically has administrative rights in the downstream product — it has to, in order to create and delete accounts. So there is now a live, privileged, unmonitored credential for a system nobody considers part of the environment any more. Decommissioning that stops at 'we turned it off in Okta' leaves exactly this behind, and it will not appear in any inventory because the app looks inactive.

Remediation

Retrieve the provisioning credential's identity from the Zoom (legacy - migrated off 2025) admin console and revoke it there — deactivating the Okta app does not revoke it. Then remove the provisioning configuration from the Okta app and delete the app. Add 'revoke downstream provisioning credentials' to your SaaS decommissioning checklist.

high NHI-006 Service account (user object)

User account appears to be a non-human identity operating as a standard user, with no MFA enrolled.

automation@example.com  ·  00uAUTOMATION0EXAMPLE
Evidence

automation@example.com scored 1.00 against a 0.50 threshold. Signals: login matches service-account naming convention (automation); no MFA factor enrolled; no interactive browser sign-in in the System Log window; 260 API events attributed to this actor. Created 2025-03-31. Admin roles held: Organization Administrator.

Business risk

automation@example.com is being used by software rather than a person, but it exists in Okta as an ordinary user. That means it is governed by the controls you designed for humans and not by the ones you would design for a machine: it will not appear in an access review as an integration, no one will be asked to re-certify it, and it survives offboarding because there is no person to offboard. It has no MFA factor enrolled, so its access rests entirely on a password — one that is almost certainly stored in a script, a CI variable, or a config file, and has probably never been rotated. It also holds an administrative role, which means a compromise of that stored password is an administrative compromise of the tenant.

Remediation

Confirm with the owning team what this account does. If it is a machine identity: assign a named human or team owner in the user profile, enrol MFA if any interactive access is still required, remove any admin role it does not demonstrably need, and plan migration of its workload to an API Service Integration so the credential is scoped and auditable rather than a password on a user object. If it is a shared human account, that is its own finding — split it into individual accounts.

medium NHI-009 Org API token

Long-lived static API token in continuous use — its expiry never takes effect.

nightly-user-sync  ·  00Tnightlyjob0000EXAMPLE
Evidence

Token 'nightly-user-sync' was created 2024-07-22 (740 days ago) and last used today. Okta's 30-day expiry runs from last use, so continuous use keeps resetting it.

Business risk

This credential has been valid for 740 days and, at the current usage rate, will remain valid forever without anyone re-approving it. It is a static bearer token: whoever holds the string has its full access, there is no MFA, no device binding, and no way to tell a legitimate call from a stolen one. Okta's own guidance is to prefer scoped OAuth 2.0 service integrations over static API tokens for exactly this reason.

Remediation

Migrate this workload to an API Service Integration using the client_credentials grant with only the scopes it needs, so access is scoped and short-lived rather than unlimited and permanent. Until then, set a calendar reminder to rotate this token on a fixed schedule and record its owning team.

medium NHI-011 Event / inline hook

Active event hook posts to an external endpoint with no authentication header configured.

legacy-audit-forwarder  ·  who002EXAMPLE
Evidence

Hook 'legacy-audit-forwarder' (who002EXAMPLE) posts to http://audit-collector.thirdparty-vendor.example.net/ingest with no authScheme set on the channel configuration.

Business risk

Without a shared secret in the request, the receiving endpoint has no way to verify that a given payload actually came from your Okta tenant. Anyone who learns the URL can post forged identity events to it. Whatever that endpoint does in response — provision an account, page an on-call engineer, write to a database — can be triggered by a stranger.

Remediation

Configure an authentication header on the hook and validate it at the receiving endpoint. Rotate the secret on the same schedule as your other credentials.

medium NHI-012 Event / inline hook

Inline hook executes synchronously inside the authentication or token-issuance path.

token-claim-enrichment  ·  cal001EXAMPLE
Evidence

Inline hook 'token-claim-enrichment' (cal001EXAMPLE) of type 'com.okta.oauth2.tokens.transform' is ACTIVE and calls https://claims.internal-tools.example.com/enrich during request processing.

Business risk

Unlike an event hook, which is fired and forgotten, an inline hook is called while Okta is deciding something. A token-transform hook can alter the claims placed in an access token; a registration or password-import hook can influence whether a request is allowed. Whoever controls claims.internal-tools.example.com therefore has influence over authorisation decisions in your tenant. There is also an availability consequence: if that endpoint is slow or down, authentication is affected for real users.

Remediation

Confirm the endpoint is owned by your organisation, not a vendor. Restrict who can deploy to it with the same rigour you apply to identity infrastructure, because that is what it is. Verify the auth header is validated on the receiving side, and monitor its latency and error rate.

medium NHI-013 SCIM provisioning connection

SCIM provisioning creates downstream users but is not configured to deactivate them.

GitHub Enterprise Cloud  ·  0oaSCIMGITHUB0EXAMPLE
Evidence

'GitHub Enterprise Cloud' (0oaSCIMGITHUB0EXAMPLE) has lifecycleCreate ENABLED and lifecycleDeactivate DISABLED.

Business risk

Offboarding is one-directional. When someone leaves, Okta removes their access to GitHub Enterprise Cloud at the front door but their account inside the downstream system stays active. If that system supports any authentication path other than SSO — a local password, a personal access token, an API key they created — the former employee still has access, and nothing in Okta will show it. This is also the finding a SOC 2 auditor is looking for when they ask you to demonstrate timely access removal: the control exists on paper, and does not fully execute.

Remediation

Enable Deactivate Users: Admin console -> Applications -> GitHub Enterprise Cloud -> Provisioning -> To App -> edit -> enable Deactivate Users. Before enabling, reconcile the existing downstream account list against current Okta users — there is likely a backlog of accounts belonging to people who have already left.

Structural recommendations

The individual findings above are symptoms. These address the conditions that produced them, and are what stops the same report being true again next year.

  • Give every non-human identity a named owning team. The recurring feature of the findings in this report is not excessive privilege — it is absent ownership. Okta has no owner field for tokens, hooks or service apps, so this must be maintained deliberately, in a naming convention or an external register.
  • Add credential revocation to offboarding. Deactivating a user does not revoke the API tokens they created, and those tokens keep their original privileges. Offboarding should explicitly check for tokens, hooks and service accounts associated with the departing person.
  • Prefer API service integrations over static API tokens. This is Okta's own guidance. Scoped OAuth credentials can be granted narrow permissions and reasoned about; a static API token silently inherits whatever its creator had.
  • Include non-human identities in access reviews. Quarterly reviews almost always cover employees only. Service accounts and integrations accumulate precisely because nothing forces anyone to re-justify them.

5  ·  Methodology, scope and limitations

What was examined

  • Org API tokens: owner, creation date, last use, expiry posture
  • API service integrations using the OAuth client_credentials grant, and their granted scopes
  • User objects assessed as probable service accounts
  • Administrative role assignments held by those accounts
  • Event hooks and inline hooks, including destination and authentication configuration
  • SCIM provisioning connections and their downstream lifecycle capabilities

What was not examined

  • Human user hygiene: stale accounts, MFA coverage, password policy
  • Credentials held in CI/CD systems (GitHub Actions, CircleCI, Jenkins)
  • Cloud IAM roles, access keys and workload identities (AWS, GCP, Azure)
  • Secrets committed to source control repositories
  • API keys created directly inside downstream SaaS applications
  • Okta Workflows connections and their stored credentials
  • Penetration testing or exploitation of any kind

Access and method

This assessment was performed with read-only API access to the Okta tenant. The tool used issues HTTP GET requests exclusively; no create, update or delete operation exists anywhere in its codebase. No configuration was changed, no credential was rotated, and no user was notified. Destination endpoints referenced by hooks were catalogued from configuration and were not contacted — probing a client's third-party endpoints is a side effect an audit should not have.

Limitations

  • Service-account detection is probabilistic. Okta has no field marking an account as non-human. Accounts were scored against four signals — naming convention, absence of enrolled MFA, absence of interactive sign-in, and presence of API activity — and reported above a threshold of 0.50. Shared human accounts (a team mailbox, a training login) can score highly and be false positives. A machine identity named like a person, or one whose credential a human occasionally uses in a browser, will be missed. Each finding lists the signals it matched so individual determinations can be contested.
  • Activity signals depend on System Log retention. "No interactive sign-in" means none within the retained log window, not none ever.
  • Point-in-time. This reflects tenant configuration as of 02 August 2026, 00:25 UTC. It is not a continuous control.

Suggested next scope

Non-human identity does not stop at the identity provider. The categories excluded above — credentials in CI/CD systems, cloud IAM roles and access keys, secrets committed to source control, and API keys held directly inside SaaS applications — typically outnumber those in Okta by a wide margin and are subject to the same absence of ownership. Extending the inventory to those systems is the natural follow-on to this engagement.
